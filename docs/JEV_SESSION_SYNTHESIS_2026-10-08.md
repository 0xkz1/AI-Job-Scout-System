# JIS・Jevに関するセッション整理

整理日: 2026-10-08。日付はJST。Codex・Claudeのローカル会話記録、決定文書、現在のJISコードを照合した。今回、パイプラインの実行・変更、有料APIへの問い合わせは行っていない。

## 結論

**Jevの単発推論が速いことと、JIS全体が速く・正確になることは別だった。** Codex側は既存の詳細レビューを維持した比較計測を選び、Claude側はJISの既存実装との比較から、今回の構成では本番の判定を置き換える根拠が不足していると判断した。

両者の方向は一致している。決定論的に解ける処理はPythonに残し、Jevは用途ごとに測り、詳細な事実監査と最終判断を省略する条件は実測から決める。Jevへの期待をきっかけに既存コードの不具合が見つかり、改善も実現したが、その改善をJevモデルの効果として数えてはいけない。

## 2. 話の変遷

### 09-19〜20: Codexがハイブリッド案の前提を修正

持ち込まれたAGYの提案では、Hermesの約1分・約4万トークンに対してJevは約0.6秒・639トークンで、型付き判定を先に置く構想だった。

Codexが同じdiffの1件を確認すると、Hermesは未接続の `worker_committed` を具体的に指摘した一方、Jevはデッドコード14%、タスク合致度9%、安全性2.94/3の「Clean」を返していた。**型が正しく、説明文を生成しないことは、欠陥を正しく検出する保証にならない。**

着地は次の順序だった。

1. 既定のHermesを維持し、APIキーの存在だけで運用を切り替えない。
2. 明示的なshadowで同一diffを両方に渡し、確率分布・入力・失敗を記録する。
3. 人間のaccept / revise / rejectを正解データとして蓄積する。
4. 詳細レビューの省略率と見逃し率を測ってから、条件付きの省略を別途決める。

セッション末では `7e06f95` を `codex/jev-hybrid-review` に実装・pushしたと報告している。**本線へのmergeや有料APIによる運用計測の完了は報告していない。** 現在の決定文書にも、09-24時点でshadow実装が本線に未統合だったという注記がある。

この決定は会話当時「ADR-015」と呼ばれ、現在の文書では番号衝突を避けて **ADR-016** に変更されている。JISコード内の「ADR-015 P0」は当時の番号を引用したもの。

### 09-22: Claudeがjevlikeと本番の接続を検証

jevlikeでは、説明文400文字と入力256バイトという二重の切り詰め、location欠落、学習対象の取り方を修正した。正規表現で判定済みの行を含めず、実際にLLMへ回る行で比較した。

| jevlikeの評価対象 | 多数決 | 入力をシャッフルした対照 | Qwen2.5-0.5B |
|---|---:|---:|---:|
| work_style、評価297件 | 50.5% | 50.5% | 50.5% |
| experience_level、評価443件 | 52.6% | 44.5% | 58.7% |

work_styleは入力を変えても予測が変わらず、置き換える意味がなかった。experience_levelは学習のシグナルが出たが、保存済みラベルへの一致率58.7%では自動代替には不足。Top-3 96.2%を使う補助案は出たが、JIS本番には接続されていない。保存済みLLMラベルとの一致は、人間が確認した正解への精度とも区別する必要がある。

クラウドJevについては、最初の確認時点でAPIキーはあってもSDKが未導入だった。その後SDKを導入し、`JIS_JEV_MODE` を追加して既定をoffにした。**インストール、有効化、改善の実証はそれぞれ別の段階だった。**

## 4. 「大幅に速くなる」が実現しなかった理由

09-23の計測では、LLM呼び出し1,269回の累積時間は4,391秒だった。matcherが2,110秒（48%）、reviewerが1,423秒（32%）、analyzerが495秒（11%）。analyzerの中央値は既に0.8秒で、Jevの測定値は約0.29秒だった。

仮にanalyzerの574呼び出しを同品質で1回0.29秒へ置き換えるという単純試算では、節約は約329秒、LLM累積時間の約7.5%。**夜間処理全体が何十倍も速くなる試算ではない。** スクレイプ時間や並列実行もあるため、累積API時間の差は夜間の実経過時間の差とも一致しない。

会話中の強い言い切りには、次の補正が必要。

- 「614 calls、中央値18.5秒、総時間16,293秒」は [STATE.md](../STATE.md) に08-27の旧測定として記録されている。Claudeの後の「測られていなかった」という発言は、この記録と矛盾する。**古い測定を09月の現状に流用していた**と整理するのが妥当。
- 「プロンプトサイズが速度を決める」は、異なるstageの比較だけでは確定できない。personaを削る小規模実験では4.50秒→2.85秒になったが、STATE.mdには別の日の計測で効果が限定的だったことと、過去に品質上の理由で短縮をrevertしたことが残る。品質を維持した本番改善は未確認。
- L1の `no_agent` は自律エージェントを起動しない意味。09-23の記録にはanalyzer・matcher等のLLM呼び出しがあり、夜間処理全体がLLMゼロだったという意味ではない。

## 5. 10-08時点のJISコードとの照合

現在の作業ツリーで確認した事実は次の通り。

- `jis_jev_judge.py` の本番コードからのimportは `jis_hermes_bridge.py` の1箇所で、書類生成後の事前監査にある。
- `check_sponsorship_jev()` と `classify_role_jev()` に本番の呼び出し元はない。関数の存在は夜間への導入を意味しない。
- 未設定・不正値の `JIS_JEV_MODE` はoff。SDKとAPIキーだけではJevの呼び出しを有効にしない。現在動いているプロセスの環境設定は今回調べていない。
- **shadowは未完成。** `is_shadowing()` は定義されているが呼び出されていない。3つの判定関数はいずれも `is_configured()`、すなわちonの場合だけAPIへ進む。現在の実装でshadowを指定しても、比較用のJev呼び出し・記録は発生しない。
- 書類監査のJev入力は会社・職種・CV先頭4,000文字・CL先頭2,500文字。**`letter_facts_v1.md` の事実台帳は渡されていない。** 現在の質問は文章の不自然さ・虚偽らしさを問うもので、候補者の実績に照らした裏付け確認にはなっていない。
- 事前監査の長さ・プレースホルダー確認はoffでも動く。offで止まるのはJev APIの判定部分であり、監査全体ではない。

SemIf / jev-review / jev-ultrafastの導入・未接続の状態は09月の会話記録による整理。今回は周辺ツールすべての現在のインストール状態を再監査していない。

## 6. 残る論点と優先順

1. **既定offを維持する。** 既存処理を置き換える根拠は今回の会話・実測からは得られていない。
2. **初期構想と実測結果を区別する。** JIS_AND_JEV.mdの速度試算・L1への導入図と、現在のAGENTS.md・コードには差がある。この整理を後続の参照先にする。
3. **次にJevを試すなら、対象を1用途に限定する。** 本番で使う入力、統一した正解ラベル、人間の判定、費用と見逃し率を比較する。書類なら主張ごとの事実台帳との照合が必要。
4. **shadowの計測経路を先に整える。** Taifunomeの設計決定とJISの実装を混同せず、既存判定を維持して比較記録が残ることを確認する。
5. **速度改善は最新の時間配分から選ぶ。** スクレイプ、matcher、reviewerを含めて測る。persona短縮は品質評価を伴う別の実験として扱う。
